# Domain Docs

Как инженерные skills должны потреблять доменную документацию этого репозитория.

## Перед исследованием кода прочитать

- **`GLOSSARY.md`** в корне репозитория.
- **`docs/adr/`**: ADR, касающиеся затрагиваемой области.

Если файлов нет — **молча продолжать**. Не сообщать об отсутствии и не предлагать создать их
заранее: `/domain-modeling` (доступен из `/grill-with-docs` и `/improve-codebase-architecture`)
создаёт их лениво, когда термин или решение реально зафиксированы.

## Структура файлов

Single-context репозиторий:

```
/
├── GLOSSARY.md
├── docs/adr/
│   ├── 0001-strapi-as-cms.md
│   └── 0003-db-sync-via-export-import.md
└── cms/
```

## Использовать словарь

Называя доменный концепт (в заголовке issue, предложении рефакторинга, гипотезе, имени теста),
использовать термин из `GLOSSARY.md`. Не скатываться к синонимам, которые словарь явно избегает.

Если нужного концепта нет в словаре — это сигнал: либо ты выдумываешь язык, которого в проекте нет
(передумай), либо есть реальный пробел (отметь для `/domain-modeling`).

## Конфликты с ADR

Если результат противоречит существующему ADR — сообщить об этом явно, а не переопределять
молча: _«Противоречит ADR-0003 (синхронизация данных через export/import), но стоит переоткрыть,
потому что…»_.
