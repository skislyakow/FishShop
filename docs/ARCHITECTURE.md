# Архитектура

## Цель

Дать Денису витрину рыбы в Telegram: покупатель листает каталог и оформляет заказ, не выходя
из мессенджера. Источник правды по каталогу и заказам — Strapi; Telegram-бот — тонкий клиент
над его REST API.

## Компоненты

```
                    Telegram Bot API
  Покупатель  <───────────────────────────>  Telegram-бот (этап 2)
  (Telegram)                                        │
     inline-кнопки                                  │ REST + API-токен
                                                    ▼
  ┌───────────────────────────────────────────────────────────┐
  │  Strapi CMS  (cms/)                                        │
  │  ├─ Content-Type Builder / Content Manager (админка)       │
  │  ├─ REST API  /api/...                                     │
  │  ├─ Media Library  (uploads/)                              │
  │  └─ .tmp/data.db  (SQLite)                                 │
  └───────────────────────────────────────────────────────────┘
        ▲                                          ▲
        │ git (код, схема, конфиг)                 │ strapi export/import
        │                                          │ (данные + uploads)
  ┌─────┴──────────────────────────────────────────────────────┐
  │  Git-репозиторий  —  общий канал для двух машин             │
  └────────────────────────────────────────────────────────────┘
```

- **Strapi (`cms/`)** — владеет каталогом и заказами. Работает на каждой машине локально.
- **SQLite (`.tmp/data.db`)** — локальная БД разработки. В git не попадает.
- **Telegram-бот (`bot/`)** — REST-клиент каталога (`bot/strapi.py`) и стейт-машина диалога
  (`bot/fsm_example.py`, python-telegram-bot 22 — ADR-0007).
- **Redis (в WSL)** — состояния диалогов бота под ключами `state:<chat_id>`; данные магазина
  не хранит.
- **Git-репозиторий** — синхронизирует код и схему между двумя машинами.
- **Экспорт-архивы** — синхронизируют данные и медиа; передаются вне git.

## Границы ответственности

- Strapi — единственный источник правды по каталогу, покупателям и заказам.
- Бот не хранит бизнес-данные: состояние диалога (в каком состоянии пользователь) живёт в Redis
  (`state:<chat_id>`) и не является данными магазина — поэтому не попадает ни в Strapi, ни в git.
- Корзина — наоборот, данные магазина: она живёт в Strapi (`Cart`/`CartItem`) и привязана к
  `telegram_user_id` (ADR-0008). В Redis остаётся только «на каком экране покупатель».
- Цена и состав заказа фиксируются в Strapi в момент оформления (см. «Позиция заказа» в
  `GLOSSARY.md`), чтобы прайс не переписывал прошлые заказы.

## Модель данных (план)

| Content-Type | UID | Ключевые поля |
| --- | --- | --- |
| Раздел | `api::category.category` | `name`, `slug`, `sortOrder`, relation `fish` (oneToMany) |
| Товар | `api::fish.fish` | `title` (string, required), `description` (text), `price` (decimal, required), `picture` (media, single); `draftAndPublish: true` |
| Корзина | `api::cart.cart` | `telegram_user_id` (string, required, unique), relation `items` (oneToMany); `draftAndPublish: false` |
| Позиция корзины | `api::cart-item.cart-item` | relation `cart` (manyToOne), relation `fish` (manyToOne), `quantity_kg` (float, required, default 1); `draftAndPublish: false` |
| Покупатель | `api::customer.customer` | `telegram_user_id` (string, required, unique), `email` (email, required); `draftAndPublish: false`; позже `name`, `phone` |
| Заказ | `api::order.order` | `status` (enum), relation `customer` (manyToOne), relation `items` (oneToMany), relation `telegramMessageId`, `comment`, `total` |
| Позиция заказа | `api::order-item.order-item` | relation `fish` (manyToOne), `quantityKg`, `pricePerKg` (снимок цены), `amount` |

## Работа с API

- База: `http://localhost:1337/api`.
- Авторизация: **API-токен** Strapi в заголовке `Authorization: Bearer <token>`.
- Токен: один `bot` (Full access) — им ходит `bot/`. Read-only токена (`bot-read`) хватало только
  на каталог: Strapi отвечает `403` на POST/PUT, поэтому добавление в корзину с ним не работает.
  Позже, если токенов станет больше, можно разделить чтение каталога и запись корзины/заказов.
- `draftAndPublish` включён для товаров: бот видит только опубликованные записи.
- У `Cart`/`CartItem` `draftAndPublish` выключен: это рабочие данные покупателя, а не контент
  для редактора. С включённым D&P записи создаются черновиками и по API не видны, а `unique`
  проверяется только при публикации.
- Каждой машине нужен свой токен — они не переносятся между инстансами; создаётся заново
  в админке: Settings → API Tokens.
- Клиент Strapi — `bot/strapi.py`: `list_fishes()` возвращает `Product`, остальной код не
  знает про HTTP, URL и токен.
- Корзина там же: `add_item()` находит корзину по `telegram_user_id` (или создаёт её), кладёт
  `CartItem` со `quantity_kg`, а повторное добавление той же рыбы увеличивает количество в
  существующей позиции. Связи ставятся передачей `documentId` в `cart` и `fish` при
  `POST /api/cart-items`.
- Чтение корзины — `get_cart()`: `GET /api/carts` с фильтром по `telegram_user_id` и
  `populate[items][populate][fish]`, возвращает `Cart`/`CartItem` (название и цена берутся из
  товара, сумма считается на месте). Бот показывает её текстом по кнопке «Моя корзина»
  (состояние `HANDLE_CART`).
- Отказ от позиции — `remove_item()`: `DELETE /api/cart-items/<documentId>`. Strapi отдаёт
  `204` и на несуществующий `documentId`, то есть удаление идемпотентное: повторный клик по
  «Отказаться» не считается ошибкой.
- На экране корзины у каждой позиции кнопка «Отказаться: …» (текст усечён до 40 знаков, у
  Telegram лимит кнопки — 64), внизу «В меню» — возврат в каталог.
- «Оплатить» показывается только в непустой корзине: бот просит почту и переходит в состояние
  `WAITING_EMAIL`. Там текст сообщения ищется регэкспом `EMAIL_PATTERN` (работает и фраза вида
  «моя почта: …»), адрес пишется в консоль `logger.info` вместе с `telegram_user_id` и
  подтверждается пользователю, после чего диалог возвращается в корзину. Мимо почты — подсказка
  и то же состояние; нажатие любой старой кнопки во время ожидания уводит в корзину или каталог,
  чтобы диалог не зависал.
- Контакт покупателя уходит в CMS: `save_customer()` — сначала `GET /api/customers` с фильтром
  по `telegram_user_id`, затем `POST /api/customers` для нового клиента или
  `PUT /api/customers/<id>`, если почту продиктовали заново: терять прежнюю запись нельзя, а
  второй клиент с тем же `telegram_user_id` упирается в `unique`. Успех виден в логе строкой
  «Клиент сохранён в CMS: documentId=…», а проверить себя можно запросом
  `GET /api/customers/<documentId>` — контакты в ответе API. Если Strapi недоступен, бот пишет
  об этом в лог и честно сообщает пользователю, что контакт остался в консоли.
- Ответ на нажатие кнопки даёт `answer_query()`: обёртка над `callback_query.answer()`, которая
  снимает «часики» и гасит `TelegramError` (таймаут через прокси, устаревший запрос) с
  предупреждением в логе. Ответ на кнопку — косметика, поэтому его сбой не должен обрывать
  хэндлер: иначе реальное действие (добавление/удаление позиции) не дошло бы до Strapi.
- Исходящие сообщения идут через `reply_text()` / `send_message()` / `send_photo()`, а они —
  через `_send()`: `NetworkError` (таймаут, обрыв прокси) повторяется до `SEND_ATTEMPTS` раз
  с паузой `SEND_DELAYS`, `RetryAfter` ждёт столько, сколько просит Telegram, а `BadRequest`
  и прочие неустранимые ошибки не ретраятся — одна строка warning и `False`. Хэндлер не рвётся:
  если запрос почты не ушёл, `ask_email()` остаётся в `HANDLE_CART`, чтобы пользователь мог
  нажать «Оплатить» ещё раз, а почта фиксируется в логе ещё до отправки подтверждения.
- Устойчивость к обрыву связи: `connect_timeout`/`read_timeout` подняты с дефолтных 5 с до
  15 с (`CONNECT_TIMEOUT`/`READ_TIMEOUT`) — handshake TLS через прокси за 5 с не успевал,
  оттуда сыпались `ConnectTimeout`. Если Telegram недоступен и дальше, `handle_users_reply`
  пишет одну строку warning вместо traceback'а и не меняет состояние: действие просто
  повторяется, когда связь вернётся. Прочие исключения по-прежнему идут в `logger.exception`
  с трейсбеком — настоящие баги прятать не нужно.

## Среды

- **Разработка** — две машины, каждая со своим Strapi и своей SQLite. Данные синхронизируются
  вручную (`docs/DB-SYNC.md`), код — через git (`docs/WORKFLOW.md`).
- **Прод** — не определён. Кандидаты: Strapi Cloud или VPS с Postgres. Зафиксируем отдельным ADR,
  когда дойдём.

## Открытые вопросы

- Единый ли API-токен для каталога и заказов или два.

## Принятые решения

- ADR-0001: Strapi как CMS и бэкенд магазина.
- ADR-0002: SQLite как локальная БД разработки.
- ADR-0003: синхронизация данных через `strapi export` / `strapi import`.
- ADR-0004: git-репозиторий как единственный кросс-машинный канал для кода.
- ADR-0005: Strapi-проект на JavaScript.
- ADR-0006: кроссплатформенный бутстрап окружения на Node-скрипте.
- ADR-0007: python-telegram-bot 22 и состояния диалога в Redis.
- ADR-0008: корзина хранится в Strapi и привязана к `telegram_user_id`.
