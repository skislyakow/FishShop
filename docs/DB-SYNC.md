# Синхронизация БД между двумя машинами

Две машины разрабатываются параллельно, у каждой — своя локальная SQLite. Код синхронизируется
через git, а **данные** (записи + загруженные файлы) — через `strapi export` / `strapi import`.

## Принцип

| Что | Канал | Куда попадает |
| --- | --- | --- |
| Код, схема content-types, конфиг, `package-lock.json` | git | `cms/src/`, `cms/config/`, `cms/package.json` |
| Записи БД (товары, разделы, заказы) | `strapi export` / `import` | архив, передаётся **вне git** |
| Медиа (фото рыбы) | внутри того же архива (`assets`) | архив, вне git |
| Секреты (`.env`, API-токены) | вручную на каждой машине | локальный `cms/.env` |
| Бинарник БД `cms/.tmp/data.db` | **нигде** — игнорируется git | — |

Обоснование — ADR-0003. Коротко: коммитить SQLite в git нельзя (бинарные конфликты, секреты,
раздувание истории), а общая удалённая БД усложняет учебный проект.

## Команды

Работать можно из корня репозитория (скрипты-обёртки не зависят от платформы):

```bash
# Выгрузить снапшот всей БД + uploads в backups/strapi-export.tar.gz
npm run db:snapshot

# Залить архив (УДАЛЯЕТ текущие данные и подменяет их содержимым архива)
npm run db:import
```

Те же команды доступны из `cms/` (`npm run db:export` и `npm run db:import`) — корневые
`db:snapshot` / `db:import` просто вызывают их через `npm --prefix cms`.

Под капотом:

```bash
strapi export --no-encrypt -f ../backups/strapi-export
strapi import -f ../backups/strapi-export.tar.gz --force
```

Полный синтаксис и опции — <https://docs.strapi.io/cms/features/data-management>.

## Снапшот по запросу

Автоматики нет: снапшот делается только когда его явно попросят. Формулировка «сделай снапшот
базы» означает одно действие — **`npm run db:snapshot` из корня репозитория**. Результат:
`backups/strapi-export.tar.gz` (записи + фото).

Импорт — отдельная сознательная команда `npm run db:import`, потому что он уничтожает локальные
данные. Полный порядок — в ритуале ниже.

## Ритуал передачи данных

Данные передаются **в одну сторону** и только когда вторая машина готова их принять.

**Машина-источник (у кого свежие данные):**

1. Убедиться, что Strapi не пишет в БД прямо сейчас (остановить dev-сервер).
2. `npm run db:snapshot` (из корня репозитория)
3. Положить `backups/strapi-export.tar.gz` в общий канал передачи (см. ниже).
4. Сообщить второй машине, что архив готов.

**Машина-приёмник:**

1. Остановить Strapi.
2. `git pull` и убедиться, что схема совпадает (`cms/src/api/**/schema.json`).
3. При необходимости запустить Strapi один раз, чтобы он применил новые content-types.
4. Положить свежий архив в `backups/strapi-export.tar.gz`.
5. `npm run db:import` (из корня репозитория)
6. Запустить Strapi и проверить каталог в админке.

### Каналы передачи архива

Архив — это обычный файл, его можно передать любым способом:

- облако/диск (Яндекс.Диск, Google Drive, Dropbox);
- файлообменник;
- защищённый архив в мессенджере;
- USB-флешка.

В git архив **не коммитим** (`backups/` в `.gitignore`).

## Правила и подводные камни

- **`import` уничтожает данные.** Он удаляет текущую БД и uploads перед импортом. Не запускай его,
  пока не выгрузил свои локальные правки (или пока они не нужны).
- **Схемы должны совпадать.** Все content-types и их поля обязаны быть идентичны на обеих машинах.
  Сначала `git pull` и старт Strapi, потом импорт.
- **Админ-аккаунт не переносится.** У каждой машины свой пользователь админки Strapi: в архив
  экспорта админы не попадают (внутри — контент и плагинные дефолты). После импорта может
  оказаться, что входить не под кем — заведи администратора заново. Поля `createdBy` / `updatedBy`
  у записей при этом пустые — это нормально.
- **API-токены не переносятся.** Создай токен заново в Settings → API Tokens и положи в `cms/.env`.
- **Версии Strapi должны совпадать.** Держи `package-lock.json` в git и ставь зависимости
  детерминированно: `npm run setup` (или `npm ci` из `cms/`).
- **Не работайте одновременно с данными на двух машинах.** Модель «одна БД — один писатель»:
  в один момент времени данные правит одна машина, потом отдаёт архив второй.
- **Медиа внутри архива.** Отдельно `uploads/` копировать не нужно, но он тоже перезаписывается
  при импорте.

## Почему не другие варианты

- **Общая удалённая БД (Postgres на Neon/Supabase):** даёт один источник правды в реальном времени,
  но добавляет внешний сервис, сеть и общий `DATABASE_URL` — лишняя сложность для учебного проекта.
  Вернуться к этому стоит при выходе в прод (см. `docs/ARCHITECTURE.md`, «Открытые вопросы»).
- **SQLite-файл в git / git-lfs:** бинарные конфликты, риск утечки секретов, раздувание истории.
